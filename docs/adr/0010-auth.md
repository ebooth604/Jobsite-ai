# ADR-0010 — Authentication: AWS Cognito

**Status:** default.
**Date:** August 2026.

## Context

Technical plan §3 says use a managed auth provider and don't build auth in-house.
Two constraints narrow the choice: data residency (§4.3) applies to user records as
much as to media, and §4's role model has a hard rule — no role, ever, sees an
individual-worker productivity view, because that view does not exist in the schema.

## Decision

**AWS Cognito**, in `ca-central-1`.

- Keeps identity data in the same Canadian region as everything else, under one
  provider, which is a simpler sentence to say to a customer's privacy officer than
  naming a second vendor and its sub-processors.
- Over Auth0: better developer experience, but a separate data-residency
  conversation and a pricing curve that bites exactly when the customer count grows.
- Roles (foreman, PM, chief estimator, VP ops, admin) are Cognito groups mapped to
  claims. **Authorization is enforced server-side per request**, never by hiding UI.

**The role model is not the privacy control.** Roles gate visibility; the absence of
per-worker columns in the schema is what makes individual productivity unavailable.
Both exist, and only the second is load-bearing (ADR-0005, technical plan §4).

## Consequences

- Cognito's hosted UI is unpleasant. Expect a custom sign-in screen against the SDK.
- Users belong to exactly one org. Multi-org access — a consultant across several
  subs — is not modelled and would need real thought.

## Reversal

**Moderate.** Sessions and claims are behind a small auth module, but a provider
change means a user migration and a password reset for every user, which is a
customer-visible event. Confirm before the first paying customer, not after.
